# Pravita Hub App Architecture

This document explains how `pravita-hub-app` works, how it uses `pravita-react-ds`, and where the boundaries currently are between shared design-system code and app-specific code.

## Repositories and responsibilities

This workspace has three related repositories:

- `pravita-hub-app`: the frontend application users run in the browser
- `pravita-react-ds`: the shared React design system package
- `pravita-hub-api`: the Spring Boot backend consumed by the app

Current responsibility split:

- `pravita-hub-app` owns routing, auth flow, API integration, page layouts, and app-specific UI
- `pravita-react-ds` currently owns theming through `DSProvider`, design tokens, Mantine theme mapping, and a small shared component surface
- `pravita-hub-api` owns authentication, registration, current-user data, and the OpenAPI contract used to generate the frontend client

## How `pravita-hub-app` consumes `pravita-react-ds`

The app depends on the design system through a GitHub dependency in [`package.json`](/Users/guevarra/workspace/pravita-hub-app/package.json):

- `pravita-react-ds: github:venerguevarra/pravita-react-ds#v0.0.2`

That means:

- the app is not using the sibling `pravita-react-ds` folder as a workspace link
- changes made in the local DS repo do not affect the app until the dependency is updated
- the app is currently pinned to tag `v0.0.2`

At runtime, the app imports `DSProvider` from `pravita-react-ds` in [`src/main.tsx`](/Users/guevarra/workspace/pravita-hub-app/src/main.tsx):

```tsx
<React.StrictMode>
  <DSProvider>
    <App />
  </DSProvider>
</React.StrictMode>
```

That is the only direct `pravita-react-ds` import currently used by the app. A repo-wide search shows no app pages or components importing DS primitives directly beyond the provider.

## Exact consumption model

`pravita-hub-app` consumes the design system in four concrete ways.

### 1. Package dependency

The app installs `pravita-react-ds` as an external package dependency from GitHub.

Implication:

- the app consumes the published package shape, not the sibling repo source directly

### 2. Theme bootstrap

The app wraps the full React tree with `DSProvider` in [`src/main.tsx`](/Users/guevarra/workspace/pravita-hub-app/src/main.tsx).

Implication:

- all Mantine components rendered by the app run under the Pravita theme context
- design tokens defined in the DS influence Mantine colors, font family, spacing, and radius defaults

### 3. Mantine theme inheritance

Even when app code imports components directly from `@mantine/core`, those components still inherit the theme generated by the DS provider.

This is why pages like:

- [`LoginPage.tsx`](/Users/guevarra/workspace/pravita-hub-app/src/pages/LoginPage.tsx)
- [`RegistrationPage.tsx`](/Users/guevarra/workspace/pravita-hub-app/src/pages/RegistrationPage.tsx)
- [`MainLayout.tsx`](/Users/guevarra/workspace/pravita-hub-app/src/layouts/MainLayout.tsx)

can use raw Mantine controls while still benefiting from DS-level theming.

### 4. Future component entrypoint

The DS exports reusable components through [`src/index.ts`](/Users/guevarra/workspace/pravita-react-ds/src/index.ts), and today that includes the shared `Button`.

Current state:

- the app is structurally ready to consume more DS components
- the app just has not migrated much of its UI surface there yet

## Consumption guidelines

These guidelines describe how `pravita-hub-app` should consume `pravita-react-ds`.

### Prefer the DS for shared primitives

If a UI primitive is meant to be reused across Pravita apps, prefer implementing it in `pravita-react-ds` and consuming it from there.

Examples:

- buttons
- form field wrappers
- cards
- badges
- section headers
- shell-level design tokens

### Keep page-specific logic in the app

If a component knows about routing, API calls, auth state, or page-specific workflows, keep it in `pravita-hub-app`.

Examples:

- login and registration forms
- dashboard-specific widgets
- route-aware navigation
- API-backed profile menus

### Use DS theming even when using raw Mantine

When you need a Mantine component that does not yet have a DS wrapper, it is acceptable to use Mantine directly inside `pravita-hub-app`.

Rule:

- prefer Mantine usage that aligns with DS tokens and tone
- avoid introducing app-local one-off visual conventions that fight the shared theme

### Promote repetition into the DS

If the same UI pattern appears in multiple pages or is likely to be reused by another Pravita app, move it toward the DS instead of copying it in the app.

Good candidates:

- repeated CTA/button group patterns
- consistent empty states
- repeated notification/banner variants
- reusable form sections

### Do not move backend-aware code into the DS

The design system should stay presentational and reusable.

Avoid pushing these concerns into `pravita-react-ds`:

- Axios clients
- auth/session logic
- route handling
- feature-specific state stores
- backend DTO knowledge

## Contributor guidelines

Use these guidelines when deciding where a change belongs and how to implement it.

### When adding UI in `pravita-hub-app`

1. Check whether an equivalent primitive already exists in `pravita-react-ds`.
2. If it exists, consume the DS component instead of rebuilding it locally.
3. If it does not exist and the need is app-specific, build it in the app.
4. If it does not exist and the need is reusable, add it to the DS first.

### When changing styles

Prefer this order:

1. DS tokens
2. Mantine theme defaults in the DS
3. shared DS component styling
4. app-local SCSS only when the styling is page- or layout-specific

That keeps the visual system coherent across apps.

### When working on both repos locally

Remember:

- `pravita-hub-app` currently points to a GitHub tag for `pravita-react-ds`
- editing the sibling DS repo does not automatically change the app

Typical workflow for DS changes:

1. update `pravita-react-ds`
2. verify the DS locally
3. publish or tag the DS version you want the app to consume
4. update the dependency reference in `pravita-hub-app`
5. reinstall dependencies in the app
6. verify the app under the new DS version

### When introducing a new shared component

Minimum bar for adding it to `pravita-react-ds`:

- export it from the DS public entrypoint
- keep props typed and reusable
- avoid app-specific business logic
- ensure it respects DS theme tokens
- add usage documentation or a story where appropriate

### When documenting usage in the app

Document both:

- what comes from the design system
- what remains app-local

That distinction matters because the current architecture is intentionally hybrid.

## What the design system currently provides

In `pravita-react-ds`, the public entrypoint is [`src/index.ts`](/Users/guevarra/workspace/pravita-react-ds/src/index.ts), which exports:

- `DSProvider`
- shared components from `src/components`

Right now the shared component catalog is very small:

- [`Button`](/Users/guevarra/workspace/pravita-react-ds/src/components/button/Button.tsx)

The design-system core consists of:

- [`DSProvider.tsx`](/Users/guevarra/workspace/pravita-react-ds/src/design-system/DSProvider.tsx)
- [`tokens.ts`](/Users/guevarra/workspace/pravita-react-ds/src/design-system/tokens.ts)
- [`mantineTheme.ts`](/Users/guevarra/workspace/pravita-react-ds/src/design-system/mantineTheme.ts)

### `DSProvider`

`DSProvider` wraps Mantine’s `MantineProvider` and adds a small context with:

- `mode`: `light` or `dark`
- `tokens`: the active token set for the selected mode
- `setMode()`: toggles the active mode

Internally it:

1. chooses `theme.light` or `theme.dark`
2. converts those tokens into a Mantine theme
3. passes that theme into `MantineProvider`

### Tokens and theme mapping

`tokens.ts` defines the Pravita design tokens:

- color ramps
- semantic colors
- typography
- radius
- spacing

`mantineTheme.ts` maps those tokens into Mantine’s theme model:

- `brand` becomes the primary Mantine color
- `neutral` is exposed as the Mantine `gray` scale
- tokenized font, spacing, and radius values are fed into Mantine theme settings

This means the DS is currently a thin theming layer on top of Mantine, not a full standalone component system.

### Shared `Button`

The shared `Button` is a wrapper around Mantine `Button` with Pravita-specific variants:

- `primary`
- `secondary`
- `subtle`

The wrapper mainly maps those variants to Mantine variants and defaults the color tone to `brand`.

## App bootstrap flow

The frontend boot path is:

1. [`src/main.tsx`](/Users/guevarra/workspace/pravita-hub-app/src/main.tsx)
2. [`src/App.tsx`](/Users/guevarra/workspace/pravita-hub-app/src/App.tsx)
3. [`src/AppRouter.tsx`](/Users/guevarra/workspace/pravita-hub-app/src/AppRouter.tsx)
4. route trees in [`src/router/PublicRouter.tsx`](/Users/guevarra/workspace/pravita-hub-app/src/router/PublicRouter.tsx) and [`src/router/ProtectedRouter.tsx`](/Users/guevarra/workspace/pravita-hub-app/src/router/ProtectedRouter.tsx)

### `main.tsx`

This file bootstraps the app and imports:

- Mantine base styles
- app SCSS bundle
- `DSProvider`

This is where the app opts into the shared design-system theme.

### `App.tsx`

This layer is intentionally thin. It only creates a `BrowserRouter` and hands off to `AppRouter`.

### `AppRouter.tsx`

The app router splits routes into:

- public routes
- protected routes behind `AuthGuard`

Protected routes are also wrapped in `RootApp`, which loads the current user before rendering the protected route outlet.

## Auth and protected-route flow

Authentication in the app is token-based and currently uses `localStorage`.

### Session check

[`src/auth/session.ts`](/Users/guevarra/workspace/pravita-hub-app/src/auth/session.ts) treats a user as authenticated if an access token exists in local storage.

### Route guard

[`src/auth/AuthGuard.tsx`](/Users/guevarra/workspace/pravita-hub-app/src/auth/AuthGuard.tsx):

- redirects unauthenticated users to `/login`
- redirects authenticated users away from `/login` to `/dashboard`
- renders child routes otherwise

### Login flow

[`src/pages/LoginPage.tsx`](/Users/guevarra/workspace/pravita-hub-app/src/pages/LoginPage.tsx):

- renders the sign-in form
- validates email/password client-side
- calls `login()` from [`src/services/authService.ts`](/Users/guevarra/workspace/pravita-hub-app/src/services/authService.ts)
- stores returned access and refresh tokens in local storage
- navigates to `/dashboard` on success

`authService.ts` calls the generated `AuthenticationApi` client and maps backend status codes into frontend-friendly login error states.

### Current-user bootstrap

After a protected route passes the auth guard, [`src/RootApp.tsx`](/Users/guevarra/workspace/pravita-hub-app/src/RootApp.tsx) loads the current user from the backend and stores it in Zustand via [`src/stores/userStore.ts`](/Users/guevarra/workspace/pravita-hub-app/src/stores/userStore.ts).

That makes `RootApp` the protected-shell bootstrap layer for user context.

## API client and backend integration

The frontend talks to the backend through an OpenAPI-generated client plus a shared Axios instance.

### Environment binding

[`src/env.ts`](/Users/guevarra/workspace/pravita-hub-app/src/env.ts) reads:

- `VITE_ENVIRONMENT`
- `VITE_PRAVITA_ADMIN_API_BASE_URL`

The backend base URL is used in both:

- [`src/http/index.ts`](/Users/guevarra/workspace/pravita-hub-app/src/http/index.ts)
- [`src/api/hubApiClient.ts`](/Users/guevarra/workspace/pravita-hub-app/src/api/hubApiClient.ts)

### OpenAPI generation

The app regenerates its API client from the checked-in spec:

- source spec: [`openapi/hub-api-docs.yaml`](/Users/guevarra/workspace/pravita-hub-app/openapi/hub-api-docs.yaml)
- generated output: `src/api/hub-api/__openapi-generated`

The important scripts in [`package.json`](/Users/guevarra/workspace/pravita-hub-app/package.json) are:

- `pnpm openapi:generate`
- `pnpm dev`
- `pnpm build`
- `pnpm typecheck`

`dev`, `build`, and `typecheck` all regenerate the client first.

### Shared HTTP client

[`src/http/client.ts`](/Users/guevarra/workspace/pravita-hub-app/src/http/client.ts) creates an Axios instance with:

- auth header injection for protected endpoints
- retry-on-refresh behavior for 401 responses
- cancellable request helpers

[`src/http/tokenStorage.ts`](/Users/guevarra/workspace/pravita-hub-app/src/http/tokenStorage.ts) stores tokens in local storage under:

- `access_token`
- `refresh_token`

### Refresh-token caveat

[`src/http/refresh.ts`](/Users/guevarra/workspace/pravita-hub-app/src/http/refresh.ts) is still placeholder code. It posts to:

- `/auth/refresh`

The file itself says it needs to be aligned with the real backend endpoint and response shape.

That means:

- login is implemented
- token persistence is implemented
- refresh behavior exists in the client abstraction
- the actual refresh endpoint integration is not fully finalized

## Practical impact for development

If you are changing these areas, use this rule of thumb.

### Change `pravita-react-ds` when:

- the change should be reusable across multiple Pravita apps
- you are updating base design tokens
- you are changing Mantine theme defaults
- you are creating a reusable component primitive

### Change `pravita-hub-app` when:

- the change is specific to auth, registration, dashboard, or app navigation
- the change depends on Pravita Hub backend behavior
- the change is a page layout or screen-specific interaction
- the change is app-only styling

## Current limitations and technical observations

- The app currently imports only `DSProvider` from the design system. Shared components are not yet widely adopted.
- The design system README describes a broader component library than what currently exists in code. In practice the DS is still early-stage.
- The app depends on a GitHub tag for `pravita-react-ds`, so local edits in the sibling DS repo are not consumed automatically.
- The refresh-token request path is still placeholder code and should be aligned with the real backend contract before relying on it in production.
- Because the OpenAPI client is generated from a checked-in YAML file, frontend API types can drift from the running backend if the spec is not kept current.

## Suggested next evolution

The most natural path from the current architecture is:

1. keep DS responsible for tokens, theming, and low-level primitives
2. gradually move reusable app UI primitives from `pravita-hub-app` into `pravita-react-ds`
3. keep route-aware and backend-aware components in `pravita-hub-app`
4. decide whether to switch from a GitHub dependency to a workspace link during active DS development

That would let the design system grow without forcing app-specific concerns into the shared package.
